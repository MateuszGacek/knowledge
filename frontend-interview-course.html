Section 01

Fundamentals Recap

Interviews often start with fundamentals because they reveal whether you can debug real UI bugs. React is not a template engine. It is a rendering runtime that turns state changes into a tree of React elements, compares that tree with the previous one, and commits minimal DOM changes.

Rendering Model

A render is a pure calculation of UI from current props, state, and context. It should not perform network calls, DOM mutation, timers, subscriptions, or logging that affects behavior.

  • Render phase: React calls components and calculates the next tree.
  • Commit phase: React applies DOM changes and runs layout/effects.
  • Strict Mode may intentionally double-invoke render/effects in development to expose unsafe logic.

Reconciliation

Reconciliation compares element type, position, and keys. Keys are not only for warnings; they define identity across renders.

  • Same component type usually preserves state.
  • Different type causes unmount/remount.
  • Changing keys intentionally resets component state.

State vs Props

Props are inputs owned by a parent. State is memory owned by a component or store. In interviews, explain ownership: the component that needs to modify the data should usually own it, unless multiple distant consumers require shared coordination.

Controlled vs Uncontrolled

Controlled components keep the source of truth in React state. Uncontrolled components keep it in the DOM and read it through refs. Controlled inputs are easier to validate and synchronize; uncontrolled inputs can reduce re-renders for large forms or simple file inputs.

controlled-vs-uncontrolled.tsx
import { useRef, useState } from "react";

export function CourierSearch() {
  const [query, setQuery] = useState("");
  const fileInputRef = useRef<HTMLInputElement>(null);

  return (
    <form>
      <input
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="Search couriers by name or region"
      />

      <input ref={fileInputRef} type="file" accept=".csv" />
    </form>
  );
}

useEffect Lifecycle, Deeply

useEffect synchronizes React with an external system: browser APIs, subscriptions, network clients, analytics, timers, storage, or third-party widgets. If you are only deriving data from props/state, you usually do not need an effect.

effect-subscription.tsx
import { useEffect, useState } from "react";

type VehiclePosition = {
  vehicleId: string;
  lat: number;
  lng: number;
};

export function useVehiclePosition(vehicleId: string) {
  const [position, setPosition] = useState<VehiclePosition | null>(null);

  useEffect(() => {
    const socket = new WebSocket(`wss://api.example.com/vehicles/${vehicleId}`);

    socket.onmessage = (event) => {
      setPosition(JSON.parse(event.data));
    };

    return () => {
      socket.close();
    };
  }, [vehicleId]);

  return position;
}
Interview answer: "Effects are for synchronization, not for calculating render data. Cleanup runs before the next effect with changed dependencies and on unmount. Dependency arrays describe values captured by the effect closure, not values I feel like watching."

Common Mistakes

  • Using array indexes as keys for sortable or editable lists.
  • Putting derived state in useState and syncing it with useEffect.
  • Mutating objects or arrays and expecting React to detect the change.
  • Ignoring cleanup for timers, event listeners, websockets, and subscriptions.

Best Practices

  • Keep render pure and deterministic.
  • Use stable domain IDs as keys.
  • Prefer derived values during render before introducing effects.
  • Make component ownership explicit: parent controls orchestration, child controls local UI detail.
When NOT to use useEffect

Do not use it to filter lists, calculate totals, copy props into state, or run logic that can happen directly inside an event handler. Effects increase the number of states your UI can be in, so treat them as integration points, not as a default control-flow primitive.

Interview questions and answers

Q: Why can React re-render without changing the DOM?

A: Rendering calculates the next React element tree. React only mutates the DOM during commit if reconciliation finds changes.

Q: What problem do keys solve?

A: Keys let React preserve or reset identity for siblings across renders. They are critical when order changes.

Q: Why is copying props to state dangerous?

A: It creates two sources of truth. The local state can become stale when parent props change.

Deep tasks and subtasks
  • Build a searchable courier table with controlled filters.
  • Refactor one derived useEffect into render-time calculation.
  • Create a sortable list and demonstrate why index keys break input state.
  • Write a custom hook with subscription cleanup and explain its dependency array.

State Management

State management is critical because most frontend complexity comes from ownership, synchronization, and invalidation. A strong interview answer separates local UI state, global client state, and server state.

State typeExamplesBest owner
Local stateDialog open, input value, selected tabComponent or custom hook
Global client stateTheme, command palette, draft workspace, selected organizationZustand or Recoil
Server stateOrders, couriers, permissions, reportsTanStack React Query

Zustand Deep Dive

Zustand is a small external store. It is excellent for imperative UI state and app-level state where normalized graphs are not required. Components subscribe to selected slices, so selector quality matters.

stores/useWorkspaceStore.ts
import { create } from "zustand";

type WorkspaceState = {
  activeDepotId: string | null;
  sidebarCollapsed: boolean;
  setActiveDepot: (depotId: string) => void;
  toggleSidebar: () => void;
};

export const useWorkspaceStore = create<WorkspaceState>((set) => ({
  activeDepotId: null,
  sidebarCollapsed: false,
  setActiveDepot: (depotId) => set({ activeDepotId: depotId }),
  toggleSidebar: () => set((state) => ({ sidebarCollapsed: !state.sidebarCollapsed })),
}));

export function DepotSwitcher() {
  const activeDepotId = useWorkspaceStore((state) => state.activeDepotId);
  const setActiveDepot = useWorkspaceStore((state) => state.setActiveDepot);

  return <button onClick={() => setActiveDepot("warsaw-central")}>{activeDepotId}</button>;
}

Recoil Atoms and Selectors Graph

Recoil models state as a graph. Atoms are source nodes; selectors are derived nodes. It fits cases where many independent pieces of state compose into derived values and where fine-grained subscriptions are useful.

state/recoil-delivery.ts
import { atom, selector } from "recoil";

type Delivery = {
  id: string;
  status: "queued" | "in_transit" | "delivered";
  priority: number;
};

export const deliveriesAtom = atom<Delivery[]>({
  key: "deliveries",
  default: [],
});

export const highPriorityDeliveriesSelector = selector({
  key: "highPriorityDeliveries",
  get: ({ get }) => get(deliveriesAtom).filter((delivery) => delivery.priority >= 8),
});

Zustand vs Recoil vs Redux

ToolStrengthTradeoff
ZustandSimple external store, low boilerplate, great for UI/app stateLess opinionated; architecture discipline is on the team
RecoilGraph-based derived state and fine-grained subscriptionsExtra mental model; ecosystem is smaller
Redux ToolkitStrict conventions, devtools, serializable event historyMore ceremony for teams that do not need it

Common Mistakes

  • Putting fetched API data into Zustand instead of React Query.
  • Creating one giant global store that becomes a hidden database.
  • Subscribing to entire Zustand state objects and causing broad re-renders.
  • Using global state because prop drilling exists two levels deep.

Best Practices

  • Classify state before choosing a library.
  • Keep actions near state transitions and use domain language.
  • Use selectors to subscribe to the smallest needed slice.
  • Do not duplicate server state in client stores.
When NOT to use global state

Avoid global state for input fields, hover state, simple modal state local to one page, or fetched data already managed by React Query. Global state should represent cross-cutting client state, not convenience.

Interview questions and answers

Q: How do you decide between Zustand and React Query?

A: React Query owns asynchronous server state, caching, retries, invalidation, and background refetching. Zustand owns synchronous client state like UI preferences or current workspace context.

Q: Why can global stores become an anti-pattern?

A: They hide ownership and lifecycle. Without boundaries, any feature can mutate any state and debugging becomes harder.

Q: When would Recoil be a better fit than Zustand?

A: When the app has many small, composable state nodes with derived selectors and fine-grained subscriptions.

  • Model a workspace store with selected depot, selected route, and panel state.
  • Move fetched order data from a global store into React Query.
  • Create a Recoil selector that derives delayed deliveries by depot.
  • Explain in writing why each state value is local, global, or server state.
Section 03

Server State with TanStack React Query v5

Server state is remote, shared, asynchronous, and can become stale without any user interaction. React Query solves caching, deduplication, retries, invalidation, background refetching, and mutation workflows.

Caching Strategy

A query key is the cache address. It should include every parameter that changes the result. In v5, gcTime replaced the old cacheTime name. In interviews, mention both if the team uses mixed terminology.

api/useOrders.ts
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { z } from "zod";
import { api } from "./axiosClient";

const orderSchema = z.object({
  id: z.string(),
  status: z.enum(["queued", "assigned", "delivered"]),
  customerName: z.string(),
});

export function useOrders(depotId: string) {
  return useQuery({
    queryKey: ["orders", { depotId }],
    queryFn: async () => {
      const response = await api.get("/orders", { params: { depotId } });
      return z.array(orderSchema).parse(response.data);
    },
    staleTime: 30_000,
    gcTime: 5 * 60 * 1_000,
  });
}

staleTime vs cacheTime/gcTime

staleTime controls freshness. While data is fresh, React Query will not refetch just because a component remounts. gcTime controls how long unused cached data stays in memory after the last observer unmounts.

Mutations and Optimistic Updates

optimistic-update.ts
export function useAssignCourier(depotId: string) {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (input: { orderId: string; courierId: string }) =>
      api.post(`/orders/${input.orderId}/assign`, { courierId: input.courierId }),

    onMutate: async (input) => {
      const key = ["orders", { depotId }];
      await queryClient.cancelQueries({ queryKey: key });
      const previous = queryClient.getQueryData(key);

      queryClient.setQueryData(key, (orders: any[] | undefined) =>
        orders?.map((order) =>
          order.id === input.orderId ? { ...order, status: "assigned" } : order,
        ),
      );

      return { previous, key };
    },

    onError: (_error, _input, context) => {
      queryClient.setQueryData(context?.key ?? [], context?.previous);
    },

    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ["orders", { depotId }] });
    },
  });
}

Error Handling

Separate transport errors, authentication errors, validation errors, and business errors. Use Axios interceptors for cross-cutting concerns, but keep domain-specific behavior near the query or mutation.

Common Mistakes

  • Using unstable query keys like raw non-serializable class instances.
  • Invalidating every query after every mutation.
  • Using React Query for local state like selected tab.
  • Setting infinite staleTime for data that must reflect operational reality.

Best Practices

  • Create query key factories for complex domains.
  • Validate API responses at runtime with Zod when backend contracts can drift.
  • Use optimistic updates only when rollback behavior is clear.
  • Prefer targeted invalidation over broad cache flushing.
When NOT to use React Query

Do not use it for purely local UI state, synchronous calculations, form drafts before submit, or state that does not represent remote data. React Query is not a replacement for all state management.

Interview questions and answers

Q: What makes server state different from client state?

A: It is owned remotely, can be changed by other users, must be fetched asynchronously, and can become stale.

Q: What is the difference between staleTime and gcTime?

A: staleTime controls freshness; gcTime controls how long inactive cached data remains before garbage collection.

Q: How do you prevent race conditions during optimistic updates?

A: Cancel relevant queries, snapshot previous data, update cache, rollback on error, and invalidate after settlement.

Deep tasks and subtasks
  • Create a query key factory for orders, couriers, reports, and depot details.
  • Implement optimistic assignment with rollback and a visible error state.
  • Define freshness rules for dashboards, detail pages, and archived reports.
  • Explain why copying query data into Zustand is usually wrong.
Section 04

Routing with React Router v7

Routing is architecture. It defines layout boundaries, data ownership, authorization gates, lazy loading, and navigation behavior. React Router v7 continues the route object and nested layout model.

router.tsx
import { lazy, Suspense } from "react";
import { createBrowserRouter, Outlet } from "react-router";

const OrdersPage = lazy(() => import("./features/orders/OrdersPage"));

function DashboardLayout() {
  return (
    <AppShell>
      <Suspense fallback={<PageSkeleton />}>
        <Outlet />
      </Suspense>
    </AppShell>
  );
}

export const router = createBrowserRouter([
  {
    path: "/",
    element: <DashboardLayout />,
    children: [
      { index: true, element: <HomePage /> },
      { path: "orders", element: <OrdersPage /> },
      { path: "orders/:orderId", element: <OrderDetailsPage /> },
    ],
  },
]);

Nested Routes and Layouts

Nested routes let parent layouts persist while child pages change. This is important for dashboards where the sidebar, header, auth context, and workspace shell should not remount on every navigation.

Navigation Patterns

Use links for user-visible navigation and imperative navigation for post-action redirects. Keep route params as part of URL state when the page should be shareable or restorable.

SPA vs MPA and SEO

SPAs provide fast client transitions and rich stateful interactions, but SEO and first load can be weaker without SSR or prerendering. For authenticated delivery dashboards, SEO is usually less important than usability, caching, and permission boundaries.

Common Mistakes

  • Using global state for route state that belongs in the URL.
  • Placing all routes in one flat list and duplicating layouts.
  • Lazy loading tiny components while leaving heavy pages eager.
  • Performing auth checks only in UI components and not in API calls.

Best Practices

  • Use layout routes for shared shells and authorization boundaries.
  • Keep route paths stable and meaningful.
  • Code split by page or heavy feature, not by every component.
  • Use search params for filters that should survive reload/share.
When NOT to put state in the URL

Do not put sensitive tokens, large draft objects, transient hover state, or purely visual animation state into the URL. URL state should be shareable, serializable, and safe to expose.

Interview questions and answers

Q: Why are nested routes useful?

A: They express UI hierarchy, preserve layout state, and keep shared shells from remounting unnecessarily.

Q: What should live in search params?

A: Shareable, serializable state such as filters, sorting, pagination, and selected view modes.

Q: What are SEO implications of an SPA?

A: Client-rendered content may be harder for crawlers and slower to first meaningful content without SSR or prerendering.

Deep tasks and subtasks
  • Design route hierarchy for dashboard, orders, couriers, reports, and settings.
  • Move table filters from Zustand into search params.
  • Add a lazy route for a heavy D3 reporting page.
  • Define auth layout boundaries for public, authenticated, and admin areas.
Section 05

Architecture and Project Structure

Good frontend architecture reduces coupling. You should be able to change the data-fetching client, form library, or route structure without rewriting every feature. Architecture is about dependency direction.

Feature-Based vs Layer-Based

Layer-based folders group by technical type: components, hooks, services. Feature-based folders group by business capability: orders, couriers, reports. For large product apps, feature-based usually scales better because ownership and change frequency align with business domains.

scalable-folder-structure.txt
src/
  app/
    router.tsx
    providers.tsx
  shared/
    api/
      axiosClient.ts
    ui/
      Button.tsx
      EmptyState.tsx
    lib/
      formatDate.ts
  features/
    orders/
      api/
        orderQueries.ts
        orderSchemas.ts
      components/
        OrderTable.tsx
      hooks/
        useOrderFilters.ts
      pages/
        OrdersPage.tsx
    couriers/
    reports/

API Layer Separation

Keep Axios configuration, request functions, schemas, and React Query hooks separated enough that each layer has one job. Avoid calling axios.get directly inside random components.

api-layer.ts
export async function getOrder(orderId: string) {
  const response = await api.get(`/orders/${orderId}`);
  return orderSchema.parse(response.data);
}

export function useOrder(orderId: string) {
  return useQuery({
    queryKey: orderKeys.detail(orderId),
    queryFn: () => getOrder(orderId),
    enabled: Boolean(orderId),
  });
}

Clean Architecture in Frontend

Clean frontend architecture means UI depends on feature contracts, not transport details. Domain concepts should not know about React components. API adapters should not decide visual behavior.

Common Mistakes

  • Creating a generic utils folder that becomes a dumping ground.
  • Mixing API response shapes directly into UI components.
  • Putting all hooks in one global hooks directory without domain ownership.
  • Over-abstracting before the second real use case exists.

Best Practices

  • Prefer feature boundaries for domain code.
  • Keep shared code truly shared and stable.
  • Define small API functions and compose them with React Query hooks.
  • Use Zod schemas at the boundary where untrusted data enters the app.
When NOT to introduce heavy architecture

Avoid complex layering for prototypes, throwaway admin screens, or tiny apps. Architecture should solve coupling and change problems, not create ceremony to look professional.

Interview questions and answers

Q: Why is feature-based structure often better for product apps?

A: It aligns code ownership with business capabilities, making changes easier to localize.

Q: What belongs in shared?

A: Stable, domain-neutral building blocks used by multiple features, such as UI primitives, API client setup, and formatting helpers.

Q: How do hooks help architecture?

A: Hooks encapsulate interaction with external systems or feature-specific state while keeping components focused on rendering.

Deep tasks and subtasks
  • Design a feature folder for reporting with API, schemas, hooks, components, and pages.
  • Refactor a component that directly calls Axios into an API function and query hook.
  • Identify which modules should be shared and which should remain feature-local.
  • Write dependency rules for app, shared, and feature folders.
Section 06

Forms and Validation with Zod

TypeScript checks your code before runtime. Zod checks untrusted values at runtime. Interviews often test whether you understand this boundary. API responses, URL params, local storage, and form submissions are untrusted until validated.

delivery-form-schema.ts
import { z } from "zod";

export const deliveryFormSchema = z.object({
  customerName: z.string().min(2, "Customer name is required"),
  address: z.string().min(8),
  priority: z.coerce.number().int().min(1).max(10),
  scheduledAt: z.string().datetime(),
});

export type DeliveryFormValues = z.infer<typeof deliveryFormSchema>;

export function parseDeliveryForm(formData: FormData) {
  return deliveryFormSchema.safeParse({
    customerName: formData.get("customerName"),
    address: formData.get("address"),
    priority: formData.get("priority"),
    scheduledAt: formData.get("scheduledAt"),
  });
}

Runtime vs Compile-Time Validation

TypeScript cannot guarantee that an API response matches your types. A type annotation can lie. Zod parses actual runtime values and returns either validated data or structured errors.

Form Patterns

Keep form drafts local unless multiple pages need them. Validate on submit for expensive forms, and validate critical fields on blur/change when fast feedback matters. Convert string inputs into domain types at the boundary, not throughout the app.

Common Mistakes

  • Assuming TypeScript validates API responses.
  • Duplicating validation rules across UI and backend without shared contracts.
  • Keeping every keystroke in global state.
  • Showing raw technical validation messages to users.

Best Practices

  • Use Zod at external boundaries: forms, API responses, local storage, URL params.
  • Infer TypeScript types from schemas to avoid duplicate type definitions.
  • Normalize data before sending it to mutations.
  • Map validation errors into user-focused messages.
When NOT to use Zod

Do not validate purely internal values already constructed by typed code unless the boundary is unclear. Over-validating every internal function call adds noise without meaningful safety.

Interview questions and answers

Q: Why use Zod if TypeScript already exists?

A: TypeScript disappears at runtime. Zod validates real values crossing external boundaries.

Q: What is the benefit of z.infer?

A: It derives TypeScript types from the schema, preventing schema/type drift.

Q: Where should validation happen?

A: At the boundary where untrusted data enters, then the rest of the app can rely on validated shapes.

Deep tasks and subtasks
  • Create schemas for order creation, courier update, and report filters.
  • Map Zod errors into field-level UI messages.
  • Validate URL search params before using them in a React Query key.
  • Explain why API types generated from OpenAPI may still need runtime validation in risky boundaries.
Section 07

Data Visualization with D3

D3 is not "a chart library"; it is a data-to-visual-primitive toolkit. Its strongest parts are scales, shapes, axes, layouts, and data transforms. In React apps, use D3 for math and React for DOM when possible.

Scales

A scale maps data domain to visual range. For example, delivery duration in minutes maps to bar width in pixels. Good scale design is the foundation of readable charts.

DeliveryDurationChart.tsx
import { scaleLinear, max } from "d3";

type Row = { courier: string; minutes: number };

export function DeliveryDurationChart({ data }: { data: Row[] }) {
  const width = 640;
  const barHeight = 32;
  const x = scaleLinear()
    .domain([0, max(data, (row) => row.minutes) ?? 0])
    .range([0, width]);

  return (
    <svg width={width} height={data.length * barHeight} role="img">
      {data.map((row, index) => (
        <g key={row.courier} transform={`translate(0 ${index * barHeight})`}>
          <rect width={x(row.minutes)} height={24} rx={6} />
          <text x={8} y={17}>{row.courier}: {row.minutes}m</text>
        </g>
      ))}
    </svg>
  );
}

Data Binding and React Integration

Classic D3 selects DOM nodes and mutates them. React also wants to own the DOM. Mixing both carelessly causes bugs. A pragmatic pattern is: D3 calculates scales/paths/layouts; React renders SVG elements.

Performance Considerations

Large visualizations can bottleneck on DOM nodes. Use canvas/WebGL for huge point clouds, virtualization for long lists, and avoid recalculating expensive layouts on every keystroke.

Common Mistakes

  • Letting D3 and React both mutate the same DOM subtree.
  • Using charts without accessible labels or data summaries.
  • Ignoring empty data, outliers, and domain padding.
  • Rendering thousands of SVG nodes without measuring performance.

Best Practices

  • Use D3 for scale and shape math; use React for rendering.
  • Keep chart dimensions explicit and responsive.
  • Handle loading, empty, error, and partial data states.
  • Use semantic titles, labels, and accessible summaries.
When NOT to use D3

Avoid D3 when a maintained charting library already covers your needs and customization requirements are low. D3 is powerful, but it transfers responsibility for accessibility, interactions, and edge cases to your team.

Interview questions and answers

Q: Why can D3 conflict with React?

A: Both can mutate DOM. If D3 changes DOM that React thinks it owns, React can overwrite or misinterpret the result.

Q: What is a scale?

A: A function that maps data values from a domain to visual values in a range.

Q: When would you choose canvas over SVG?

A: When rendering very large numbers of marks where DOM node count becomes too expensive.

Deep tasks and subtasks
  • Create a depot performance bar chart with D3 scales and React-rendered SVG.
  • Add empty, loading, and error states.
  • Document why SVG or canvas is the right rendering target.
  • Add an accessible chart summary for screen readers.

3D Graphics with Three.js, React Three Fiber, and Drei

Three.js wraps WebGL into a scene graph. React Three Fiber maps that scene graph into React components. Drei provides useful helpers like cameras, controls, loaders, and environment presets.

WebGL Basics

WebGL renders on the GPU. A 3D scene needs a renderer, scene, camera, geometry, material, lights, and a render loop. R3F hides much of the setup but not the performance constraints.

DepotMap3D.tsx
import { Canvas, useFrame } from "@react-three/fiber";
import { OrbitControls } from "@react-three/drei";
import { useRef } from "react";
import { Mesh } from "three";

function DeliveryNode({ delay }: { delay: number }) {
  const meshRef = useRef<Mesh>(null);

  useFrame((_, delta) => {
    if (meshRef.current) meshRef.current.rotation.y += delta;
  });

  return (
    <mesh ref={meshRef} position={[delay, 0, 0]}>
      <boxGeometry args={[1, 1, 1]} />
      <meshStandardMaterial color={delay > 5 ? "tomato" : "seagreen"} />
    </mesh>
  );
}

export function DepotMap3D() {
  return (
    <Canvas camera={{ position: [0, 4, 8] }}>
      <ambientLight intensity={0.5} />
      <directionalLight position={[3, 5, 2]} />
      <DeliveryNode delay={3} />
      <DeliveryNode delay={7} />
      <OrbitControls />
    </Canvas>
  );
}

Performance Tips

Avoid creating new geometries, materials, and textures every render. Dispose resources when needed. Use instancing for many repeated objects. Keep render-loop work small and avoid React state updates every frame.

Common Mistakes

  • Updating React state inside useFrame on every frame.
  • Creating materials inline for thousands of objects.
  • Ignoring GPU memory and texture sizes.
  • Using 3D where a 2D chart would communicate better.

Best Practices

  • Use R3F declarative components but remember the underlying Three.js objects.
  • Memoize or reuse heavy resources when appropriate.
  • Use instanced meshes for repeated objects.
  • Profile FPS and memory on target devices.
When NOT to use 3D

Avoid 3D for standard dashboards, basic charts, or accessibility-critical workflows where spatial interaction adds cognitive load without business value.

Interview questions and answers

Q: What are scene, camera, and mesh?

A: The scene contains objects, the camera defines the viewpoint, and a mesh combines geometry with material.

Q: What does R3F abstract?

A: It lets you express Three.js scene objects as React components and coordinates rendering through React.

Q: Why avoid setState in every frame?

A: It forces React reconciliation at frame rate. Direct refs are often better for per-frame 3D updates.

Deep tasks and subtasks
  • Create a 3D depot scene with delayed deliveries highlighted.
  • Replace repeated meshes with instancing.
  • Measure FPS before and after optimization.
  • Explain when a 2D D3 visualization is better than R3F.

Drag and Drop: dnd-kit vs react-dnd

Drag and drop libraries differ in mental model. dnd-kit is modern, accessible, and excellent for sortable UI. react-dnd is backend-based and strong for complex drag sources/drop targets, including tree-like interactions.

LibraryBest forTradeoff
dnd-kitSortable lists, boards, accessible interactionsYou build more domain behavior yourself
react-dndComplex drag source/drop target systems, custom backendsMore abstraction and setup complexity
sortable-routes.tsx
import { DndContext, DragEndEvent } from "@dnd-kit/core";
import { SortableContext, arrayMove } from "@dnd-kit/sortable";

export function RouteStopSorter({ stops, setStops }: Props) {
  function handleDragEnd(event: DragEndEvent) {
    const { active, over } = event;
    if (!over || active.id === over.id) return;

    const oldIndex = stops.findIndex((stop) => stop.id === active.id);
    const newIndex = stops.findIndex((stop) => stop.id === over.id);
    setStops(arrayMove(stops, oldIndex, newIndex));
  }

  return (
    <DndContext onDragEnd={handleDragEnd}>
      <SortableContext items={stops.map((stop) => stop.id)}>
        {stops.map((stop) => <SortableStop key={stop.id} stop={stop} />)}
      </SortableContext>
    </DndContext>
  );
}

Common Mistakes

  • Using array indexes as draggable IDs.
  • Updating server order on every hover instead of committed drop.
  • Ignoring keyboard accessibility.
  • Mixing layout animation and drag transforms without testing.

Best Practices

  • Use stable IDs for drag identity.
  • Keep optimistic reordering local and persist after drop.
  • Provide keyboard and screen reader affordances where possible.
  • Choose react-dnd when drag types/backends matter more than sorting.
When NOT to use drag and drop

Avoid drag and drop when ordering can be handled with explicit priority fields, bulk actions, or simple buttons. DnD is harder to test, less discoverable, and often weaker on mobile/accessibility.

Interview questions and answers

Q: Why are stable draggable IDs important?

A: They preserve item identity across reorders and prevent state from attaching to the wrong item.

Q: When choose react-dnd over dnd-kit?

A: For complex drag sources/drop targets, custom backends, or tree interactions where sortable-first abstractions are not enough.

Deep tasks and subtasks
  • Build a sortable delivery-stop list with optimistic save on drop.
  • Add keyboard-accessible reorder controls.
  • Compare implementation complexity between dnd-kit and react-dnd for a tree view.

Section 11

Authentication with Auth0 and JWT

Authentication proves identity. Authorization decides access. A JWT is a signed token containing claims, but it is not encrypted by default. Anyone who has it can read its payload; only the signature prevents tampering.

JWT Structure

JWTs have three parts: header, payload, signature. The payload may include sub, aud, iss, exp, scopes, roles, and tenant claims. Never store secrets in the payload.

auth0-axios.ts
import axios from "axios";
import { useAuth0 } from "@auth0/auth0-react";

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
});

export function useAuthenticatedApi() {
  const { getAccessTokenSilently } = useAuth0();

  async function request<T>(path: string) {
    const token = await getAccessTokenSilently();
    const response = await api.get<T>(path, {
      headers: { Authorization: `Bearer ${token}` },
    });
    return response.data;
  }

  return { request };
}

Token Storage Strategies

In SPAs, token storage is a security tradeoff. Memory storage reduces persistent XSS exposure but loses tokens on reload. Local storage survives reload but is exposed to XSS. HttpOnly cookies reduce JS access but require CSRF-aware design. Auth0 SDKs generally handle much of this flow.

Common Mistakes

  • Putting sensitive information into JWT payloads.
  • Trusting decoded JWT claims on the frontend as the final authority.
  • Storing long-lived tokens in local storage without understanding XSS risk.
  • Only hiding buttons instead of enforcing authorization on the backend.

Best Practices

  • Use short-lived access tokens and refresh/rotation through the provider.
  • Attach tokens at the API boundary, not throughout random components.
  • Handle 401/403 differently: unauthenticated vs unauthorized.
  • Enforce permissions server-side.
When NOT to decode JWT on the client

Do not use client-decoded claims as a security boundary. They can help optimize UI display, but backend authorization must decide real access.

Interview questions and answers

Q: Is a JWT encrypted?

A: Usually no. Standard JWTs are signed, meaning tampering can be detected, but payload contents are readable.

Q: Why is local storage risky for tokens?

A: Any successful XSS can read local storage and exfiltrate tokens.

Q: What is the difference between 401 and 403?

A: 401 means not authenticated; 403 means authenticated but not allowed.

Deep tasks and subtasks
  • Design an Auth0 provider wrapper for a Vite app.
  • Add token injection to the API layer without leaking auth concerns into UI components.
  • Define UI behavior for loading, unauthenticated, unauthorized, and expired-session states.
  • Explain the security tradeoffs of memory, local storage, and HttpOnly cookie approaches.

Internationalization with i18next

Section 13

Performance Optimization

Performance work starts with measurement. In React interviews, show that you understand causes of re-render, network waterfalls, bundle size, expensive computations, layout thrashing, and poor caching.

Re-render Causes

  • Component state updates.
  • Parent re-renders causing child function execution.
  • Context value identity changes.
  • External store subscriptions changing.
  • Query results changing due to fetch/invalidation.
memoization-boundary.tsx
import { memo, useMemo } from "react";

const ExpensiveTable = memo(function ExpensiveTable({ rows }: { rows: OrderRow[] }) {
  return <DataGrid rows={rows} />;
});

export function OrdersView({ orders, status }: Props) {
  const visibleRows = useMemo(
    () => orders.filter((order) => order.status === status),
    [orders, status],
  );

  return <ExpensiveTable rows={visibleRows} />;
}

Memoization

useMemo, useCallback, and React.memo are optimization tools, not correctness tools. They help when referential stability prevents expensive child work or expensive calculations. They add complexity and can be useless if dependencies change every render.

Code Splitting

Split by routes and heavy features: D3 reports, R3F scenes, admin panels, and rarely-used import/export workflows. Do not split every small component.

Common Mistakes

  • Adding memoization everywhere without profiling.
  • Passing unstable object literals to memoized children.
  • Using one massive context value for frequently changing state.
  • Shipping heavy chart/3D code on the initial dashboard route.

Best Practices

  • Measure first with React Profiler, browser performance tools, and bundle analysis.
  • Move state down when only a small subtree needs it.
  • Use virtualization for large tables/lists.
  • Code split heavy routes and features.
When NOT to memoize

Do not memoize cheap calculations, components that always re-render due to changing props, or code where readability suffers more than performance improves. Memoization has maintenance cost.

Interview questions and answers

Q: Does React.memo prevent all re-renders?

A: No. It shallowly compares props. Context changes, state changes, and changed prop references still trigger work.

Q: What is a common context performance problem?

A: A provider passes a new object value frequently, causing all consumers to re-render.

Q: How do you optimize a slow page?

A: Measure, identify bottleneck, choose targeted optimization, verify improvement, and avoid speculative complexity.

Deep tasks and subtasks
  • Profile a dashboard and identify the top three render costs.
  • Split a heavy reports page with lazy loading.
  • Replace one broad context with smaller providers or external-store selectors.
  • Explain why a chosen memoization boundary is worth the complexity.

Testing with Playwright

E2E tests validate user-critical flows across browser, network, routing, rendering, and integration points. They are more expensive than unit tests, so focus on business-critical paths.

test("dispatcher assigns courier to an order", async ({ page }) => {

What to Test

Test user outcomes: authentication, navigation, core CRUD flows, permission behavior, critical filters, error states, and high-risk integrations. Do not assert implementation details.

  • Test critical paths, not every implementation branch.

  • Keep tests independent and deterministic.
  • Capture traces/screenshots for debugging CI failures.

Build Tools: Vite, TypeScript, and Environment Configuration

Build tools affect developer experience, production output, environment configuration, and performance. Vite uses native ESM during development and Rollup for production builds.

Vite vs Webpack

ProductionRollup-based buildWebpack bundling pipeline
ConfigSimpler defaults for modern appsVery flexible, often more complex

Bundling vs Transpiling

Transpiling converts syntax, such as TypeScript or modern JavaScript, into browser-compatible JavaScript. Bundling combines modules, optimizes chunks, and rewrites imports for deployment.

env.d.ts
interface ImportMetaEnv {

Environment Variables

In Vite, only variables prefixed with VITE_ are exposed to client code. Anything exposed to frontend code is public from a security perspective. Never put backend secrets in frontend env variables.

Common Mistakes

  • Putting secrets in VITE_ variables.
  • Assuming TypeScript checking happens automatically during every Vite build unless configured.
  • Ignoring bundle size from heavy libraries.
  • Using environment variables without runtime deployment validation.

Best Practices

  • Run type checking in CI with tsc or project references.
  • Validate required env variables during app startup or build.
  • Code split heavy features and inspect production chunks.
  • Keep secrets on the server; frontend env values are public configuration.
When NOT to customize build tooling

Avoid custom build plugins or clever config until a real constraint requires it. Build tooling complexity can slow onboarding and make CI failures harder to diagnose.

Interview questions and answers

Q: Why is Vite fast in development?

A: It serves source modules over native ESM and avoids bundling the entire app before startup.

Q: Are VITE_ variables secret?

A: No. They are bundled into client code and visible to users.

Q: What is the difference between bundling and transpiling?

A: Transpiling changes syntax; bundling combines modules and optimizes output chunks.

Section 16

Advanced TypeScript

Strong frontend candidates use TypeScript to encode domain constraints, not just to annotate props. Advanced TypeScript is about narrowing unsafe input, preserving inference, modeling impossible states, and making refactors safer without turning the codebase into unreadable type gymnastics.

Generics

Generics let functions, components, and helpers preserve type information from the caller. In production, use them when a utility must work across multiple shapes while still returning precise types.

query-result.ts
type ApiResult<TData> =
  | { status: "success"; data: TData }
  | { status: "error"; message: string };

function unwrapResult<TData>(result: ApiResult<TData>): TData {
  if (result.status === "error") {
    throw new Error(result.message);
  }

  return result.data;
}

Discriminated Unions

Discriminated unions are the best way to model UI states because they prevent impossible combinations such as isLoading: true and data being required at the same time.

ui-state.tsx
type OrdersState =
  | { type: "loading" }
  | { type: "error"; message: string }
  | { type: "empty" }
  | { type: "ready"; orders: Order[] };

function OrdersContent({ state }: { state: OrdersState }) {
  switch (state.type) {
    case "loading":
      return <Spinner />;
    case "error":
      return <ErrorState message={state.message} />;
    case "empty":
      return <EmptyState />;
    case "ready":
      return <OrderTable orders={state.orders} />;
  }
}

Utility Types, Narrowing, unknown vs any

unknown forces validation before use. any disables type safety and should be isolated to migration boundaries. Utility types like Pick, Omit, Partial, and Record are useful when they express domain intent, not when they hide unclear models.

type-guard-zod.ts
import { z } from "zod";

const courierSchema = z.object({
  id: z.string(),
  name: z.string(),
  active: z.boolean(),
});

type Courier = z.infer<typeof courierSchema>;
type CourierUpdate = Partial<Pick<Courier, "name" | "active">>;

function parseCourier(value: unknown): Courier {
  return courierSchema.parse(value);
}

Common Mistakes

  • Using any to silence real uncertainty instead of validating with Zod or narrowing.
  • Creating clever generic types that nobody can maintain.
  • Representing UI states with many booleans instead of discriminated unions.
  • Duplicating Zod-inferred types manually and letting them drift.

Best Practices

  • Prefer unknown for untrusted input and narrow deliberately.
  • Use discriminated unions for async and workflow states.
  • Infer types from Zod schemas at runtime boundaries.
  • Keep advanced types readable enough for the whole team.
When NOT to use advanced TypeScript

Do not use complex conditional types or overloaded generics to avoid writing clearer domain models. If the type is harder to understand than the runtime problem, it is likely over-engineered.

Section 17

API Client Architecture: Axios, OpenAPI, Zodios, and Validation

API client architecture controls how the frontend talks to the backend, how errors are normalized, where tokens are attached, how generated contracts are consumed, and how runtime validation protects the app from contract drift.

Axios Client and Interceptors

Use one configured client per backend boundary. Interceptors are appropriate for request IDs, auth headers, tracing metadata, and normalized error wrapping. Avoid business-specific decisions inside global interceptors.

axios-client.ts
import axios, { AxiosError } from "axios";
import { z } from "zod";

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  timeout: 15_000,
});

const apiErrorSchema = z.object({
  code: z.string().optional(),
  message: z.string(),
  traceId: z.string().optional(),
});

export function normalizeApiError(error: unknown) {
  if (axios.isAxiosError(error)) {
    const parsed = apiErrorSchema.safeParse(error.response?.data);
    return {
      status: error.response?.status ?? 0,
      message: parsed.success ? parsed.data.message : "Unexpected API error",
      traceId: parsed.success ? parsed.data.traceId : undefined,
    };
  }

  return { status: 0, message: "Unknown client error" };
}

OpenAPI-Generated Clients and Zodios

OpenAPI generation gives compile-time request/response types and reduces manual drift. Zodios combines API endpoint definitions with Zod schemas, making runtime validation and typed calls part of the same contract. In projects using openapi-zod-client, generated schemas should be treated as boundary contracts, not leaked into every UI component if the UI needs a different view model.

zodios-client.ts
import { Zodios } from "@zodios/core";
import { z } from "zod";

const orderSchema = z.object({
  id: z.string(),
  status: z.enum(["queued", "assigned", "delivered"]),
});

export const zodiosApi = new Zodios(import.meta.env.VITE_API_URL, [
  {
    method: "get",
    path: "/orders/:orderId",
    alias: "getOrder",
    response: orderSchema,
  },
]);

const order = await zodiosApi.getOrder({ params: { orderId: "ord_123" } });

Request/Response Typing and Error Normalization

API functions should return validated domain data or throw normalized errors. Components should not parse Axios error shapes. React Query hooks can then map normalized errors into retry, boundary, or inline fallback behavior.

Common Mistakes

  • Calling Axios directly from components and duplicating error handling.
  • Trusting generated TypeScript types without validating risky runtime boundaries.
  • Putting token refresh logic inside every query function.
  • Leaking backend DTOs into UI when the UI needs a stable view model.

Best Practices

  • Centralize transport configuration and cross-cutting headers.
  • Keep generated clients at the API boundary.
  • Normalize errors into a small app-level error shape.
  • Map API DTOs to UI models when the backend shape is unstable or overly broad.
When NOT to generate a client

For a very small or unstable prototype API, generation can slow iteration. For a real product with many endpoints and teams, generated contracts usually pay for themselves quickly.

Section 18

React Error Handling: Error Boundaries, Suspense, and Async Failures

Production-grade React apps need planned failure states. Error handling is not only a toast. It includes render error isolation, async error normalization, query retries, fallback UI, logging, and recovery paths.

Error Boundaries

Error boundaries catch render-time errors in their child tree. They do not catch event handler errors, rejected promises by default, server errors outside render, or errors thrown asynchronously after render.

ErrorBoundary.tsx
import { Component, ReactNode } from "react";

type Props = { children: ReactNode; onReset?: () => void };
type State = { error: Error | null };

export class ErrorBoundary extends Component<Props, State> {
  state: State = { error: null };

  static getDerivedStateFromError(error: Error): State {
    return { error };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportErrorToMonitoring({ error, componentStack: info.componentStack });
  }

  render() {
    if (this.state.error) {
      return (
        <FeatureCrashFallback
          onRetry={() => {
            this.props.onReset?.();
            this.setState({ error: null });
          }}
        />
      );
    }

    return this.props.children;
  }
}

Suspense and Query Error Boundaries

Suspense coordinates loading fallback for components that suspend. React Query can integrate with Suspense and error boundaries, but the team must define where fallback boundaries live: page, feature panel, or small widget. Coarse boundaries are simpler; fine-grained boundaries preserve more of the UI when one area fails.

query-boundary.tsx
import { QueryErrorResetBoundary } from "@tanstack/react-query";
import { Suspense } from "react";

export function OrdersBoundary() {
  return (
    <QueryErrorResetBoundary>
      {({ reset }) => (
        <ErrorBoundary onReset={reset}>
          <Suspense fallback={<OrdersSkeleton />}>
            <OrdersPage />
          </Suspense>
        </ErrorBoundary>
      )}
    </QueryErrorResetBoundary>
  );
}

Async Errors

Event handlers and async callbacks need explicit handling. Use mutation error states, try/catch in event flows, normalized API errors, and logging. Do not expect a render error boundary to catch every failure.

Common Mistakes

  • Assuming error boundaries catch async errors from event handlers.
  • Wrapping the entire app in one boundary and showing a blank crash screen for small widget errors.
  • Retrying non-retryable 400/403 errors.
  • Showing only a toast for critical data-load failures without recovery UI.

Best Practices

  • Place boundaries around route and feature-level failure domains.
  • Normalize API errors and map them to retry, auth, validation, or fatal UI states.
  • Use Suspense intentionally, with fallback boundaries that match UX expectations.
  • Log errors with enough context to debug without leaking sensitive data.
When NOT to use Suspense

Avoid Suspense if the team has not agreed on fallback boundaries and data-fetching conventions. Inline loading states may be clearer for forms, mutations, or partial widgets where preserving stale data matters.
